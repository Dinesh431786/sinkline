# Guard Surprisal: detecting conditionally-triggered supply-chain malware

**Date:** 2026-07-26
**Status:** Approved design, not yet implemented
**Goal:** research-grade, publishable novelty with a falsifiable evaluation

---

## 1. Problem

Malicious code in package repositories is usually caught by syntactic scanners
because it is blunt: exfiltrate on import, run a shell command in `setup.py`.
The residue those scanners cannot reach is the *conditionally triggered* tail —
payloads that stay dormant until a rare condition holds:

```python
if random.random() < 0.005 and socket.gethostname() == "build-07":
    os.system(payload)
```

Bandit and Semgrep see `os.system` with a non-constant argument and score it the
same whether it is guarded by nothing or by a one-in-a-million trigger. They
match syntax; the distinguishing property here is *semantic and quantitative*.

**The signal is not severity. It is severity conditioned on improbability.**

## 2. Contribution

**Guard surprisal** — for each dangerous sink, the number of bits of trigger
condition that must be satisfied to reach it:

```
bits = −log₂ P(reach sink)
```

Benign code reaches `os.system` under ordinary conditions (≈0 bits). The example
above sits behind roughly `−log₂(0.005) + −log₂(P(hostname match))` ≈ 8 + 16 = 24
bits. The metric is computable, interpretable to a reader and to a user
("this sink is behind 24 bits of trigger"), and structurally out of reach for a
pattern matcher.

### 2.1 Scope of the claim — read this before writing any abstract

Most real supply-chain malware has **no trigger at all**. The DataDog corpus is
dominated by unconditional exfiltration on import or install. Guard surprisal
scores those zero, correctly, because there is no guard to measure.

Therefore the claim is **not** "a better malware detector". The claim is:

> Guard surprisal detects conditionally-triggered payloads that syntactic
> scanners structurally cannot flag, measured as *added detections over a
> Bandit/Semgrep baseline*, at a measured false-positive cost.

"We find N packages nobody else flags, and here is our FP rate" is defensible.
"We detect 94% of everything" is not, and invites exactly the attack that
sinks the paper.

## 3. Components

### 3.1 `guards.py` — guard extraction

**Dangerous sink** means, precisely, a call site already reported by the existing
engine under `DANGEROUS_SINK`, `COMMAND_INJECTION`, `INSECURE_DESERIALIZATION`,
`OBFUSCATED_PAYLOAD` or `CREDENTIAL_EXFILTRATION`. This work adds no new sink
definitions; it only measures what guards the ones already found.

For each such call site, produce the **guard set**: the conjunction of branch
conditions dominating that call, followed interprocedurally.

- Reuses `taint.py` for cross-file call resolution.
- Reuses `symbolic_engine.py`'s condition walker for the per-condition AST.
- Output: `list[GuardedSink]`, each holding the sink finding, the ordered guard
  predicates, and the source spans for evidence.

### 3.2 `priors.py` — predicate → probability

Three tiers. **The tiering is the part that has to survive review**, so each
predicate's tier is recorded in the output, never blended away.

| Tier | Example | Probability |
|---|---|---|
| **Analytic** (exact) | `random.random() < c` | `c` |
| | `random.randint(a,b) == k` | `1/(b−a+1)` |
| | `random.random() > c` | `1−c` |
| **Calibrated** (measured) | `os.environ.get(X) == "lit"` | from prior table |
| | `socket.gethostname() == "lit"` | from prior table |
| **Unknown** | anything unrecognised | **treated as common** |

**The unknown rule is the primary false-positive control.** An opaque condition
must never manufacture surprisal. If unknown predicates defaulted to "rare",
every benign configuration check would become a finding. Unknown contributes
≈0 bits and is counted and reported.

A **predicate shape** is the predicate with its literal operands erased, keeping
the callee and comparison: `os.environ.get(·) == <str>` is one shape,
`socket.gethostname() == <str>` another. Shapes are what gets counted, because
the specific literal (`"build-07"`) is exactly what varies between attacks.

The calibrated table is generated by measuring, over the benign corpus, how
often each predicate shape gates a dangerous sink. It is checked into the
repository as data with provenance: source corpus, date, sample count. It is
**not** learned weights and there is no model — the table is inspectable, and
any reviewer can regenerate it.

### 3.3 `trigger_rarity.py` — scoring

Combine predicate probabilities via **z3 model counting**, not a naive product.
Two conditions on the same variable are correlated; multiplying them fabricates
rarity. Model counting over the joint constraint handles this.

Emits finding `TRIGGERED_PAYLOAD` carrying: computed bits, the guard chain, and
the tier of each predicate.

**Time-based guards are reported as dormancy, not probability.** A date
comparison (`date.today() > D`) is not a coin flip; folding it into a
probability is the easiest thing in this design for a reviewer to attack. Dormant
payloads get their own finding category and their own row in the results.

## 4. Evaluation

### 4.1 Corpora

| Corpus | Role | Notes |
|---|---|---|
| [Backstabber's Knife Collection](https://dasfreak.github.io/Backstabbers-Knife-Collection/) | development | 174 real packages, DIMVA'20, comparable to published work |
| [DataDog malicious-software-packages-dataset](https://github.com/DataDog/malicious-software-packages-dataset) | **held out** | 17,367 human-vetted npm/PyPI packages |
| Top 5,000 most-downloaded PyPI | benign | for FP rate and for prior calibration |

The benign set is split: calibration draws the prior table from one half, the
false-positive rate is measured on the other. Calibrating and measuring FP on
the same packages would report a number that means nothing.

### 4.2 Two-stage gate

1. Develop and tune on Backstabber's, where every case can be inspected by hand.
2. Freeze the method **and the prior table**.
3. Run once on DataDog as held-out test.

The harness enforces this: the frozen artefact is hashed, and the held-out run
records that hash. Tuning against the test set should be mechanically
impossible, not merely discouraged.

### 4.3 Metrics

- **Added detections over baseline** (Bandit + Semgrep, standard rulesets) — the headline.
- False-positive rate on the benign corpus.
- Per-category recall, split conditional vs unconditional.
- **Ablation:** analytic-only priors vs hybrid, to show what calibration buys.
- Count of unknown predicates encountered, and of solver timeouts.

### 4.4 Safety — this is live malware

- Samples are **never executed**: decrypt to a quarantined directory, static
  parse only, no import, no `setup.py` invocation.
- The harness refuses to run if asked to import corpus code.
- Quarantine directory is gitignored and never scanned by the repo's own CI.

## 5. Degradation and error handling

- **z3 absent** (it is absent on the current dev machine): fall back to analytic
  priors under an independence assumption, and mark results `degraded=True`.
  Degraded results must not be reportable as headline numbers.
- **Per-sink solver timeout**: counted and reported, never silently swallowed.
- **Unparseable file**: counted as an error, excluded from both numerator and
  denominator, and reported — consistent with the `files_scanned` rule that
  counts must never overstate.

## 6. Testing

- Unit tests per prior tier, including exact values for analytic predicates.
- Explicit test that unknown predicates yield ≈0 bits, using benign config-check
  patterns as the fixtures.
- Property test: surprisal is monotone in guard count for independent guards.
- Correlated-guard test: two conditions on one variable must not multiply.
- Existing 65-sample corpus retained as a regression gate.

## 7. Prerequisites (separate from the algorithm)

1. **Rename `QUANTUM_*` categories and `quantum_*` modules** to what they
   actually detect. There is no quantum computation in Python taint analysis;
   the naming reads as a credibility problem and would sink the paper.
2. **Reconcile README (94% recall) with BENCHMARK.md (100% category / 93.5%
   CI-gate).** Contradictory headline numbers already in the repository
   undermine any new claim made alongside them.

## 8. Explicitly out of scope

- Machine-learned classification. The calibrated table is measured frequency,
  not a model.
- Concolic or sandboxed execution of samples.
- npm/JavaScript support. Python only.
- Any change to the existing detection categories beyond the rename in §7.

## 9. Related work to differentiate from

[Detecting Python Malware in the Software Supply Chain with Program
Analysis](https://rshariffdeen.com/paper/ICSE25-SEIP.pdf) (ICSE'25 SEIP) applies
program analysis to this same corpus. **Read it before claiming novelty.** The
distinction to establish: that work detects malicious behaviour; this work
quantifies *how well hidden* the behaviour is, and uses that quantity as the
discriminator.
